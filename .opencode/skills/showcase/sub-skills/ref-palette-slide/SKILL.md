# ref-palette-slide

把「参考图配色」→「配色规范」→「一页 16:9 PPT」这条链路固化成可复用流程。

适用场景：拿到一张品牌页 / 封面 / 收尾页作为**配色来源**，另有一张信息图 / 一段大纲作为**内容来源**，
需要输出一张配色统一、可直接放进演讲的内容页。

---

## 设计系统（v2）— 先读这一节

这套 skill 的产出以**可读性优先**，不以"塞得下"为荣。三条硬约束：

### 1. 字号下限 10pt（硬门禁）

`MIN_PT = 10.0`，在 `add_text()` 里**统一强制**——所有 layout、chip、图标、页脚都继承，
没有任何地方能绕过。生成后用 `--check` 会逐 run 扫描并报出违规：

```bash
python3 scripts/build_slide.py --content c.json --out s.pptx --check
# -> checks OK (inside 16:9 canvas; every run >= 10pt)
```

**推论：内容装不下时，砍内容，不要缩字号。** 这是本 skill 最重要的一条纪律。

### 2. 密度预算

10pt 下限意味着单页能承载的信息量是有限的。预算表：

| 约束 | 值 | 说明 |
| :--- | :--- | :--- |
| 单页文字层级 | ≤ 3 层 | 例如：标题 / 正文 / 注释。不要再加第四层 |
| 单个列表项 | ≤ 4 条 | `MAX_LIST = 4`。第 5 条起请拆页 |
| 单列文字块 | ≤ 2 个 | 一列里最多"一段说明 + 一个结论" |
| 单个文本块 | ≤ 3 行 | 超过就说明这句话该被砍掉一半 |
| 表格单元格 | ≤ 12 字 | 单元格是索引，不是句子 |

### 3. 视觉语言

- **无装饰条**：卡片顶部不加色条；标题下不加装饰横线。
- **无嵌套盒子**：面板里不再套盒子。强调靠 **tint + 字号**，不靠描边。
- **一处一色块**：一页里只允许一个"实色大色块"承担结论（如底部结论条）。
- **示意图不套面板**：浅色 tint 元素直接浮在卡片白底上。

### 4. 字号阶梯（可直接抄）

| 元素 | 字号 |
| :--- | :--- |
| 页面主标题 | 26–28pt Bold |
| 副标题 | 11pt |
| 区块/团队名 | 15–19pt Bold |
| 主体正文 | 10.5–11.5pt |
| 注释 / 标签 / 页脚 | **10pt**（下限） |
| 数字强调（柱状图数值） | 16pt Bold |

## Workflow

### Step 1 — 解读参考图配色（产出「配色要求」）

1. `extract_palette.py` 拿到主色 + 占比 + 角色建议。
2. **人工补一层语义解读**：源图里每种颜色"在表达什么"（品牌主色？动线？背景？）。
   脚本给的是数值，语义必须自己写。
3. 把结果整理成一份 `color-spec.md`（模板见 `assets/color-spec.md`），至少包含：
   - 核心色 token 表（HEX）
   - **语义约定**（一个颜色只表达一个含义）
   - **面积比例**（60/30/10）
   - 文字与对比度规则
   - 组件级配色表
   - 禁止事项（源图没有的颜色一律不许引入）

> 关键判断：先看源图**有没有暖色**。没有暖色的品牌色板，内容页也绝不能引入红/橙/紫，
> 否则"串味"。负向信息改用深中性色（`slate`）+ 白字表达。

### Step 2 — 内容建模

把内容源（信息图/大纲）拆成结构化 JSON，字段见 `assets/content.example.json`：

- `title_lead` / `title_accent`：标题拆两段，**accent 段用副色（蓝）** 承担焦点。
- `stages[]`：流程节点。每个节点含 `name` / `desc` / `level` / `cap` / `bar`(色条) / `icon`。
  - `level` 走 **成熟度色阶**（灰→绿单向渐变）。
  - 瓶颈节点用 `tag` + `border`（蓝）标出。
  - 终态节点用 `fill: green_dark` + 白字。
- `boards[]`：对比看板（如"过去 vs 现在"）。每个 `column` 含 `name` / `count` / `items[]` / `accent`。
  - `accent` 只从 `slate | blue | green_soft | green_tint` 里选。

### Step 3 — 生成 + 自检

```bash
python3 scripts/build_slide.py --content <content.json> --palette <palette.json> --out slide.pptx --check
```

`--check` 做**几何自检**：所有形状是否越出 16:9 画布。先过这一关再渲染。

### Step 4 — 视觉 QA（必做，但成本高）

```bash
./scripts/render_slide.sh slide.pptx out/
```

然后**用子 agent 看渲染图**（不要自己看，你会看到你期望的东西）：

```
Assume there are issues — find them. 检查：元素重叠、文字溢出/被裁、
装饰线是按单行文本定位的但标题换行了、间距不均、边距 < 0.5"、
列宽不一致、低对比度文字、占位符残留。
```

至少完成一轮「发现问题 → 修复 → 复验」。

## 布局模板说明

`build_slide.py` 内置十二套单页模板（画布固定 13.333" × 7.5"），由内容 JSON 的
`layout` 字段选择。**改版式时只改 `draw_*` 里的坐标常量，不要动 `PALETTE` 的语义分工。**

### `layout: "pipeline-boards"`（默认）

适合：端到端流程 + 前后对比。示例：`assets/content.example.json`

```
┌───────────────────────────────────────────────────────────────────┐
│ 编码自动化了，需求还是手工作坊                        28pt        │  0.28–0.88
│ 副标题 11pt                                                       │  0.94–1.26
├───────────────────────────────────────────────────────────────────┤
│ ⬤Idea  ⬤需求分析  ⬤设计  ⬤编码  ⬤测试  ⬤部署  ⬤运营  ⬤价值实现    │  1.34–2.58
│         [L0~L1]  [L2]  [L3~L4] [L3~L4] [L4~L5] [L4~L5]           │
│         ↑ 只保留「图标 + 名称 + 等级徽章」三层，desc/caption 全部砍掉│
├─────────────────────────────┬─────────────────────────────────────┤
│ 过去：需求 backlog 做不完    │ 现在：开发在等需求                  │  2.76–7.04
│                             │                                     │
│   52   18   15   12   8     │   38   27   12   6   4   3          │  ← 16pt 数值
│   ██   ▄    ▄    ▄    ▂     │   ██   █    ▄    ▂   ▂   ▂          │  ← 柱高 ∝ 数量
│  需求  设计  开发  测试  上线 │  Idea  需求  设计  开发 测试 上线    │  ← 10pt 列名
│                             │                                     │
│ ▌主要问题：backlog 积压严重  │ ▌主要问题：开发在等需求             │  6.36–6.92
└─────────────────────────────┴─────────────────────────────────────┘
```

关键字段：
- `stages[]`：`level` 走成熟度色阶；`tag`+`border` 标瓶颈；`icon` 见 `draw_icon`。
  **不再渲染 `desc` / `cap`** —— 8 列在 10pt 下放不下第三层文字。
- `boards[]`：每列只要 `name` + `count`。渲染成**柱状图**（柱高 ∝ 数量），
  而不是卡片堆叠。信息量骤降但"积压堵在哪一段"一眼可见，比一堆小卡片更有效。
  两块的柱高各自按本块峰值归一，看的是**形状**而不是绝对值。

### `layout: "pain-cards"`

适合：N 个并列痛点 / 能力项，每项需要一张示意图。示例：`assets/content.pain-cards.example.json`

```
┌───────────────────────────────────────────────────────────┐
│ 标题(lead+accent) 28pt                                    │  0.34–0.94
│ 副标题（关键词蓝色加粗 + 说明灰色）                        │  1.00–1.32
├──────────┬──────────┬──────────┬──────────┬───────────────┤
│ 01       │ 02       │ 03       │ 04       │ 05            │  1.74  30pt 浅蓝序号
│ 标题 15pt│ 标题     │ 标题     │ 标题     │ 标题          │  2.32–3.22
│ 描述10.5 │ 描述     │ 描述     │ 描述     │ 描述          │  3.30–4.14
│  示意图  │  示意图  │  示意图  │  示意图  │  示意图        │  4.28–6.88
│ (无面板) │ (无面板) │ (无面板) │ (无面板) │ (无面板)      │  浮在卡片白底上
└──────────┴──────────┴──────────┴──────────┴───────────────┘
```

**设计意图：刻意"去模板化"**
- 卡片**没有描边、没有顶部装饰条**，只靠白色面 + 浅绿白底色的微差分层。
- 编号用**大号浅蓝数字 `01`–`05`**，不用实心圆形徽章。
- 示意图**不套面板**，浅色 tint 直接浮在卡片白底上；也**不套第二层框**。
- 字号整体放大（标题 13pt / 描述 8.5pt），留白优先。

关键字段：
- `cards[].illustration` 选内置示意图，`illus` 传该图所需参数。
- `subtitle_runs`（可选）替代 `subtitle`：结构是 `[[[文本, 覆盖属性], ...]]`，
  即"段落列表 → 段内 run 列表"，可做关键词加粗变色。
- `subtitle`（v2 起**不再渲染**）：卡片只保留「序号 → 标题 15pt → 描述 10.5pt → 示意图」
  三层。原来的 subtitle + 典型表现两层已删除，为 10pt 下限腾出空间。
- 示意图内部的列表一律取前 4 条（`labels[:4]`、`steps[:5]`、`bubbles[:3]`），
  超出的部分请在内容侧删掉，不要指望渲染器替你压缩。

| `illustration` | 语义 | `illus` 参数 |
| :--- | :--- | :--- |
### `layout: "breakthrough"`

适合：**"现状 → 破局"** 的转折页——左证问题、右给答案。示例：`assets/content.breakthrough.example.json`

```
┌──────────────────────────────────────────────────────────────────┐
│ 如果需求过程想要达到 L3（L3 用副色）                              │  0.32–0.90
│ 副标题：从 L0~L1 … 跨到 L3 …                                     │  0.96–1.28
│                                                                  │
│      ┌现在┐              ┌目标┐                                  │  1.32
│  ●───┴─●──┴───────◎──────┴────●─────●                           │  1.76  成熟度轨道
│  L0     L1      L2     L3     L4    L5                          │  1.98
├──────────────────────────────────────────────────────────────────┤
│ ⚙ 工具    ▸▸ 流程   ●● 组织   ▤ 知识   ☺ 人                      │  2.34
│ [现状]        [现状]      [现状]    [现状]    [现状]              │
│ 问题…         问题…       问题…     问题…     问题…              │
│      ↓             ↓           ↓         ↓        ↓             │
│ ┌────────┐   ┌────────┐  ┌────────┐ ...                         │  4.48–6.10
│ │[破局]  │   │[破局]  │  │[破局]  │        ← blue_tint 面板      │
│ │ 方案…  │   │ 方案…  │  │ 方案…  │                             │
│ └────────┘   └────────┘  └────────┘                             │
├──────────────────────────────────────────────────────────────────┤
│ ▌五个维度里，四个可以靠设计解决 —— 只有「人」，必须自己决定。▌     │  6.26–6.98
└──────────────────────────────────────────────────────────────────┘
```

关键字段：
- `scale.levels` / `scale.now{from,to,label}` / `scale.target{index,label}`：
  成熟度轨道。轨道**复用 `LEVEL_COLORS` 色阶**，"现在"段用色阶原色，
  "现在→目标"区间用蓝色填充表示"要补的差距"，目标之后（L4/L5）转灰表示"暂不在范围"。
  这一条轨道就是本页与前面"成熟度 L0–L5"那页的锚点。
- `columns[].icon ∈ gear | flow | people | doc | person`，`problem` / `solution` 各一段。
- `problem_label` / `solution_label`：两个小标签的文案，默认 `现状` / `破局`。
- `thesis`（可选）：底部整幅结论条。**只放一句话**，否则会抢走正文的注意力。

**设计意图**：`破局` 面板是本页唯一的"色块"，用 `blue_tint` 而不是描边盒子；
`现状` 完全不加底色，靠灰色文字退到背景。这样读者的视线会自然落在"答案"上。

### `layout: "team-fit"`

适合：**分型 → 匹配** 页。上半是一张"分类标尺"（N 个维度 × 3 档），
下半是若干张团队卡，每张卡给出**企业实例**并映射到一个方案层。
示例：`assets/content.team-fit.example.json`

```
┌──────────────────────────────────────────────────────────────────────┐
│ 三类流程，各归其位：先给团队分型，再选流程形态                        │  0.30–1.24
├──────────────────────────────────────────────────────────────────────┤
│            决策链路   协作界面   影响面      规则密度    生命周期      │  1.18
│ ▍轻 ▍  PM一人可定  1–2角色  内部可回滚  技术属性强  一次性           │  1.54  ← 浅绿行带
│ ▍中 ▍  融合拍板   3–4角色  单业务线    中等编排    持续迭代          │  1.98  ← 浅蓝行带
│ ▍重 ▍  分离会签   5+跨部门 资金/合规   密集跨域    长周期复用        │  2.42  ← 浅灰行带
├──────────────────────────────────────────────────────────────────────┤
│ ┌ L1·极简交付 ┐ ┌ L2·轻量产品 ┐ ┌ L3·业务产品 ┐                      │  3.00
│ │ 小型工具团队 │ │ 单业务线产品 │ │ 跨部门业务   │                    │
│ │ 一句话画像   │ │ 一句话画像   │ │ 一句话画像   │                    │
│ │ 企业示例     │ │ 企业示例     │ │ 企业示例     │                    │
│ │ [实例1][实例2][实例3]           ← 层色 tint 胶囊                  │
│ │ 平衡点：…    │ │ 平衡点：…    │ │ 平衡点：…    │                    │
│ └──────────────┘ └──────────────┘ └──────────────┘                   │
└──────────────────────────────────────────────────────────────────────┘
```

关键字段：
- `scale.rows[]`（`label` + `tone ∈ green|blue|slate`）× `scale.dimensions[].cells[]`（长度必须等于行数）。
- `teams[].tone` 决定整张卡的层色（chip / 实例胶囊 / 平衡点文字）。
- `teams[].examples[]` 建议 **2–3 条**，每条一句话、能在 1 行内读完；
  写成"谁做的什么系统"而不是抽象名词，否则失去"结合企业实际"的意义。
- `teams[].balance{label,value}`：这一层在优化什么（取自三力拉扯的平衡点）。

**设计意图**：`tone` 在"标尺行"和"团队卡"之间复用同一套绿/蓝/板岩，
让读者不需要连线就能看出"哪一档 → 哪一种团队 → 哪一类流程"。

### `layout: "swimlane"`

适合：**分层治理蓝图**——把「谁负责 / 做什么 / 用什么 skill / 敲什么命令 / 产出什么」
叠成泳道。示例：`assets/content.swimlane-l1| l2 | l3.example.json`
（转写自 `learning-sdd/visuals/workflow-blueprint.html` 的三张图）

```
┌──────────────────────────────────────────────────────────────────────┐
│ [01] 极简交付 · Layer 01                    [SPEC-DRIVEN DEVELOPMENT]│  0.28–1.04
│      Minimalist Delivery / Single Change Pipeline                    │
├──────────┬───────────────────────────────────────────────────────────┤

│ │ ▤  │  交付即结束  ──▶  持续维护资产                                 │  3.28
│ └────┘                                                               │
│ ┌────┐                                                               │
│ │ ↻  │  抛给开发    ──▶  闭环协同                                     │  4.58
│ └────┘                                                               │
├──────────────────────────────────────────────────────────────────────┤
│ ▌需求工程师从「写文档的人」变成「设计需求结构的人」▌                 │  6.06–6.98
└──────────────────────────────────────────────────────────────────────┘
```

关键字段：
- `precondition{label, text}`：**一条前置判断**。放在最前面，因为它决定后面走哪条路。
- `shifts[].icon ∈ structure | assets | loop`：**每条转变配一个图标**。
  - `structure` = 2×2 方格（设计结构）
  - `assets` = 圆柱体 `CAN`（资产仓）
  - `loop` = 环形箭头 `CIRCULAR_ARROW`（闭环）
- `shifts[].from / to / text`：`from` 渲染成**灰胶囊**（现状），`to` 渲染成**层色实心胶囊**（目标），
  中间一个箭头。`from` 是固定宽度 2.10″，**所以文案要短**（≤6 字），否则会撑破。
- `conclusion{lead, sub}`：第一行 15pt 粗（结论），第二行 11pt（补充）。

**设计意图**：这类"新要求"页最容易写成三条并列的长句，读者记不住。
这里做了两件事让它可记忆：
1. **灰胶囊 → 彩胶囊**：把"从 X 到 Y"变成两个可以看见的状态，而不是一句话。
2. **一图标一转变**：图标承担记忆锚点，文字负责解释。
   （人记图标比记句子牢；三条转变 = 三个图标 = 三个锚点。）

**结论句的写法**：不要用"从 A 变成 B"这种对称句式套一个听起来高级的 B。
本页初稿写的是「内容生产者 → 系统设计者」，被指出不准确——
因为"系统设计者"既过宽（PM 不设计系统），又漏掉了维护与协同两个面。
改成「写文档的人 → 设计需求结构的人」后，**设计对象是具体的（需求结构），不是泛的（系统）**。
给角色下定义时，宁可把对象写窄写实，也不要写大。

### `layout: "rollout"`

适合：**演讲最后一页**——N 阶段路径 + 一行 Tips + 一句收尾金句。
示例：`assets/content.rollout.example.json`

```
┌──────────────────────────────────────────────────────────────────────┐
│ 规模化落地：三个阶段，不要一步到位                            26pt   │  0.28–0.86
├──────────────────────────────────────────────────────────────────────┤
│ ┌─① 单点跑通─┐▶┌─② 沉淀基线─┐▶┌─③ 规模化──┐                        │  1.30–4.02
│ │ 范围：…     │ │ 范围：…     │ │ 范围：…    │                        │
│ │ 动作：…     │ │ 动作：…     │ │ 动作：…    │                        │
│ │ ┌目标───┐   │ │ ┌目标───┐   │ │ ┌目标──┐  │  ← 层色浅底           │
│ └─┴───────┴───┘ └─┴───────┴───┘ └─┴──────┴──┘                        │
│ 落地 Tips                                                            │  4.16
│ ┌────┐┌────┐┌────┐┌────┐┌────┐                                       │  4.46–5.70
│ │门禁││指标││Noop││纪律││路径│  ← 5 张灰底小卡，各 1 行标题 + 1 行注   │
│ └────┘└────┘└────┘└────┘└────┘                                       │
├──────────────────────────────────────────────────────────────────────┤
│ ▌把产能建在结构上，而不是建在个人身上。▌                             │  5.96–6.96
│ ▌工具 2 小时就能学会；结构只能靠组织纪律和 peer review 长出来。▌      │
└──────────────────────────────────────────────────────────────────────┘
```

关键字段：
- `phases[].no / name / tone / scope / action / goal`：
  `scope` 是"这一步覆盖多大范围"（1 个 Epic → 1 个域 → 多域），**它让阶段有递进感**；
  `goal` 放在层色浅底块里，是这一步"要证明什么"。
- `tips[].title / sub`：**title 必须压进 1 行**（≤14 字），sub 最多 2 行。
  超过就把 tip 删掉——5 条是上限，不是目标。
- `closing{lead, sub}`：`lead` 16pt 粗，是全场最后一句话，**只放一句**；
  `sub` 11pt 做补充，可以稍微长一点。

**设计意图**：结尾页承担三件事——**给路径（可执行）、给 Tips（避坑）、给一句话（记住）**。
三者缺一，听众散场后只会记得"讲了很多"。
所以这里的密度顺序是：路径最详细、Tips 最简、金句最大。

**收尾金句的写法**：不要复述前文，要给一个"可带走的判断"。
本页的 `lead` 把整场的论点压成一句——
"把产能建在结构上，而不是建在个人身上"。

## Common Gotchas

1. **Keynote 会"抢"文档**（macOS 渲染最大的坑）
   Keynote 的 Resume 会把用户之前打开的 deck 一起恢复。如果脚本写
   `set theDoc to front document`，导出的会是**用户的 deck**，而你还以为渲染成功了。
   `render_slide.sh` 的做法：复制成唯一文件名 → 打开 → **按文档名定位** → 只导出/关闭这一个。
   永远不要 `close every document`。

2. **sips 只能转 PDF 第一页**
   本模板是单页，够用。多页请用 `pdftoppm`（poppler）或 LibreOffice 后端。

3. **中文字体要同时设 `latin` 和 `ea`**
   只设 `run.font.name` 不会作用于中文，必须写 `<a:ea typeface="...">`。
   `build_slide.py` 的 `_set_run_font()` 已经处理。

4. **圆角矩形 `adjustments[0]` 是相对 `min(w,h)` 的比例，不是绝对半径**
   想要 0.1" 圆角，值应该是 `0.1 / min(w, h)`。传错会让容器变成胶囊或完全方角。

5. **10pt 下限会强制你砍内容——这是设计意图，不是 bug**
   早期版本为了"忠实还原源图"把字号压到 6–7pt，结果投影上读不出来。
   现在 `MIN_PT` 会拦下任何小于 10pt 的 run；如果你发现内容放不下，
   正确处理是**减少条目 / 拆页 / 砍掉重复的表达**，而不是调低 `MIN_PT`。
   把 `--min-pt` 调小只应用于「打印稿」这类特殊场景，不要用于演讲投影。

6. **不要用 `…` 之外的占位符**
   看板里的 `…` 是"截断"语义，用 `gray_soft` 底 + `gray_mid` 字；不要用 "Lorem" / "TBD"。
